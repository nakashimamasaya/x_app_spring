# 要件定義（MVP）

X(Twitter) 風のメッセージアプリ。**MVP のスコープは「投稿・タイムライン・いいね・フォロー」＋認証・プロフィール**。

スコープ外の機能は [スコープ外](#スコープ外) を参照。ここに書かれていない機能は作らない。

---

## 1. アクター

| アクター | 説明 |
|---|---|
| ゲスト | 未認証。公開タイムラインと個別投稿・プロフィールの閲覧のみ |
| ユーザー | 認証済み。投稿・いいね・フォロー・自分のプロフィール編集ができる |

アカウントは**すべて公開**。非公開アカウント（承認制フォロー）は MVP では作らない。

---

## 2. ユースケース

### UC-1 ユーザー登録

1. ゲストが username / email / password / displayName を入力する
2. username と email の重複がなければアカウントを作成する
3. 登録しただけではログイン状態にならない。続けてログインが必要

**受け入れ条件**
- username が既存と重複したら `409`
- email が既存と重複したら `409`
- バリデーション違反は `400`（違反フィールドを列挙して返す）
- メール確認は行わない（スコープ外）

### UC-2 ログイン / ログアウト

1. username と password でログインする
2. Access Token（短命）をレスポンスボディで受け取る
3. Refresh Token は HttpOnly Cookie で受け取る（JS から読めない）
4. Access Token 失効時は Refresh でサイレントに再取得する
5. ログアウトすると Refresh Token が失効し Cookie が消える

**受け入れ条件**
- 認証失敗は `401`。username が存在しない場合とパスワード誤りで**レスポンスを区別しない**（ユーザー列挙攻撃を防ぐため）
- Refresh のたびに Refresh Token をローテーションする
- 失効済み Refresh Token が再提示されたら、そのユーザーの全 Refresh Token を失効させる（トークン盗難の検知）
- ログイン試行にはレート制限を掛ける（超過は `429`）

### UC-3 投稿する / 削除する

1. ユーザーが本文（1〜280 文字）を入力して投稿する
2. 投稿は即座に自分と自分のフォロワーのホームタイムラインに現れる
3. 自分の投稿は削除できる

**受け入れ条件**
- 本文が空、または 280 文字超なら `400`
- 他人の投稿を削除しようとしたら `403`
- 削除は論理削除。削除済み投稿は取得・一覧の両方から消える（`404`）
- 未認証の投稿は `401`

### UC-4 タイムラインを見る

| 種類 | 対象 | 認証 |
|---|---|---|
| ホーム | 自分＋フォロー中ユーザーの投稿 | 必要 |
| 公開 | 全ユーザーの投稿 | 不要 |

**受け入れ条件**
- 新しい順（`createdAt` 降順）
- カーソルページングで取得する（オフセットは使わない）
- 削除済み投稿は含まない
- 認証済みで閲覧した場合、各投稿に「自分がいいね済みか」が含まれる

### UC-5 いいねする / 外す

1. 投稿にいいねを付ける / 外す
2. 投稿にはいいね数が表示される

**受け入れ条件**
- **冪等**。既にいいね済みの投稿に再度いいねしても `204`（`409` にしない）
- いいねしていない投稿のいいねを外しても `204`
- 自分の投稿にもいいねできる
- 存在しない・削除済みの投稿は `404`

### UC-6 フォローする / 外す

1. 他ユーザーをフォローする / 外す
2. プロフィールにフォロー中数・フォロワー数が表示される

**受け入れ条件**
- **冪等**（UC-5 と同じ理由）
- **自分自身はフォローできない**（`400`）
- 存在しないユーザーは `404`
- フォロー承認は不要（全アカウント公開のため）

### UC-7 プロフィールを見る / 編集する

1. username 指定で任意ユーザーのプロフィールを見る
2. 自分の displayName と bio を編集する

**受け入れ条件**
- プロフィールには投稿数・フォロワー数・フォロー中数を含む
- 認証済みで閲覧した場合、「自分がフォロー中か」が含まれる
- **email はどのレスポンスにも含めない**（自分自身のプロフィールでも返さない）
- 編集できるのは自分のみ。username は変更不可

## 3. 画面構成

```
/                     公開タイムライン（ゲストも閲覧可）
/login                ログイン
/register             ユーザー登録
/home                 ホームタイムライン（要認証）+ 投稿フォーム
/posts/:id            投稿詳細
/users/:username      プロフィール + そのユーザーの投稿一覧
/users/:username/followers    フォロワー一覧
/users/:username/following    フォロー中一覧
/settings/profile     プロフィール編集（要認証）
```

未認証で要認証画面にアクセスしたら `/login` にリダイレクトし、ログイン後に元の画面へ戻す。

## 4. バリデーション規則

仕様の正は `api/openapi.yaml`。ここは一覧としての再掲。

| 項目 | 規則 |
|---|---|
| `username` | 3〜20 文字 / `^[a-zA-Z0-9_]+$` / 大文字小文字を区別せず一意 |
| `email` | RFC 準拠のメール形式 / 最大 254 文字 / 一意 |
| `password` | 8〜72 文字（72 は BCrypt の上限）/ 文字種の縛りは設けない |
| `displayName` | 1〜50 文字 |
| `bio` | 0〜160 文字 |
| 投稿本文 | 1〜280 文字。前後の空白は除去した上で判定する |
| `limit` | 1〜100（既定 20） |

**文字数は Unicode コードポイント数で数える**。絵文字（サロゲートペア）を 2 文字と数えない。

## 5. 非機能要件

学習・実験用プロジェクトのため、本番運用相当の可用性は求めない。

| 項目 | 目標 |
|---|---|
| レスポンス | タイムライン取得（20件）が p95 で 300ms 以内（ローカル Docker 環境） |
| 想定データ量 | ユーザー 1,000 / 投稿 100,000 程度で性能が破綻しないこと |
| 同時接続 | 10 程度（開発・デモ用途） |
| ブラウザ | 最新の Chrome / Safari / Firefox |

### セキュリティ要件

BFF を挟まずブラウザから API を直接叩くため、以下は必須とする。

- Access Token は**メモリ保持のみ**。localStorage / sessionStorage に保存しない（XSS 時の被害を限定するため）
- Refresh Token は HttpOnly / Secure / SameSite=Strict Cookie。パスを `/api/v1/auth` に限定し、通常の API リクエストに載せない
- CORS の許可オリジンは環境変数で明示指定する。ワイルドカードは使わない
- パスワードは BCrypt でハッシュ化する
- Refresh Token は**ハッシュ化して保存**する（DB 漏洩時にそのまま使われないため）
- 認証系エンドポイントにレート制限を掛ける
- エラーレスポンスにスタックトレースや内部の識別子を含めない

### 監視

- `/actuator/health` でヘルスチェックを提供する
- 本番相当プロファイルでは Swagger UI と DevTools を無効化する

---

## 6. スコープ外

必要になった時点で別途計画する。**MVP では作らないと明示的に決めた**もの。

- 返信・リポスト（スレッド構造）
- 画像・動画の添付
- リアルタイム通知（SSE / WebSocket）
- 検索、ハッシュタグ、メンション
- ミュート・ブロック、非公開アカウント
- DM
- OAuth ソーシャルログイン、メールでのログイン、パスワードリセット、メールアドレス確認
- 投稿の編集
- 多言語対応（UI は日本語のみ）
- タイムラインの fan-out on write（MVP は購読側で都度集計する fan-out on read）
