# 0006. カウンタを非正規化しない

- ステータス: 採用
- 日付: 2026-07-28

## 背景

いいね数・フォロワー数・投稿数の持ち方。`posts.like_count` のようなカラムを持って
更新時に増減させるか、都度 `COUNT` で集計するか。

## 決定

非正規化せず、都度集計する。`users` と `posts` にカウンタカラムを持たない。

## 理由

非正規化は**正しさとのトレードオフ**であり、性能問題が実在してから払うべき代償。

カウンタカラムを持つと、以下のバグが構造的に入り込む:

- いいね削除時の減算漏れ → 実際より多い数が永久に表示される
- 二重加算（リトライ、競合）
- ユーザー削除時のカスケードでカウンタが同期されない
- 一度ズレると、再集計バッチを書くまで直らない

**このバグは「間違った数が表示され続ける」という形で現れ、テストで検出しにくい。**

MVP の想定データ量はユーザー 1,000 / 投稿 100,000。この規模なら
`likes (post_id)` インデックスを張った `COUNT` は十分速い。
性能上の問題が存在しないうちに、正しさを犠牲にする理由がない。

## 結果

- カウンタが常に正しい。同期処理もリカバリバッチも不要
- **N+1 に注意が必要。** 一覧で投稿ごとに `COUNT` を撃つと即座に破綻する。
  投稿一覧と集計は `LEFT JOIN` + `GROUP BY`（または相関サブクエリ）で**1 クエリにまとめる**
- このクエリは Spring Data のメソッド名クエリでは表現できないため、
  JPQL またはネイティブクエリを手書きする。**ローカル LLM に任せない領域**

## 見直す条件

- タイムライン取得が p95 300ms を超えたとき（まずクエリと実行計画を確認し、
  インデックスで解決できないと確認できてから非正規化する）
- 投稿数が 100 万件規模になったとき

非正規化する場合は、**再集計バッチとその検証も同時に作る**こと。
カウンタを足すだけでズレたときに戻せなくなる。
