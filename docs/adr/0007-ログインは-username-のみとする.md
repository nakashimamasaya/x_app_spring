# 0007. ログインは username のみとする

- ステータス: 採用
- 日付: 2026-07-28

## 背景

登録時に email を受け取るのに、ログインは username のみとする。
「email で登録したのに email でログインできない」のは一見ちぐはぐに見えるため、判断を残す。

選択肢は 3 つあった。

1. `username` のみ
2. `email` のみ
3. `login` という 1 フィールドで username / email の両方を受け付ける

## 決定

`LoginRequest { username, password }` とし、**username のみ**でログインする。

## 理由

**選択肢 3 を捨てた理由が主。** 1 フィールドで両方受け付けると、

- `"alice@example.com"` は username なのか email なのか、という判定ロジックが必要になる
- username の文字種は `^[a-zA-Z0-9_]+$` なので `@` を含めず判定自体は可能だが、
  **バリデーションエラーのメッセージが書けなくなる**
  （「username の形式が不正」なのか「email の形式が不正」なのか決められない）
- 契約テストのケースが「username で成功／email で成功／どちらでもない文字列」と増える

**選択肢 2 を捨てた理由**: プロフィール URL が `/users/{username}` である以上、
username は必ず存在する。ログイン識別子を email にすると識別子が 2 系統になる。

**選択肢 1 の弱点**は「email を登録させておいて使わない」ことだが、
email はパスワードリセット（スコープ外）のために保持しており、無駄ではない。

## 結果

- `LoginRequest` は `username` + `password` の 2 フィールド。バリデーションが素直
- 認証失敗時は、**username が存在しない場合とパスワード誤りを区別しない**。
  どちらも同一の `401` を返す（ユーザー列挙攻撃を防ぐため）
- ユーザーが username を忘れた場合の復旧手段が無い。
  MVP はスコープ外だが、パスワードリセットを実装する際に併せて対応すること

## 見直す条件

- パスワードリセットを実装するとき（email での本人確認が入るため、
  ログイン識別子としての email も同時に検討する）
