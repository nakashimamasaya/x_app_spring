# 0004. email をレスポンスに含めない

- ステータス: 採用
- 日付: 2026-07-28

## 背景

`email` は登録時に受け取り DB に保存するが、API レスポンスで返すかどうか。
`GET /users/me` で自分自身の email を返すのは一見自然に見える。

## 決定

**email はいかなるレスポンスにも含めない。** 自分自身のプロフィールであっても返さない。
OpenAPI のスキーマ定義にも `email` プロパティを一切書かない。

## 理由

MVP には email を表示する画面が無い。「いつか使うかもしれない」で公開すると、

- Entity をそのまま返す実装が紛れ込んだとき、他人の email まで漏れる余地が生まれる
- 「`/users/me` なら OK、`/users/{username}` なら NG」という**条件付きのルール**になり、
  レビューで見落としやすい

**「どこにも出さない」は例外の無いルールなので機械的に検査できる。**
スキーマに存在しなければ、契約テストが漏洩を検出できる。

BFF を置かず API がブラウザに直接晒される構成（[0001](./0001-bff-を採用しない.md)）では、
DTO の設計ミスがそのまま情報漏洩になる。条件付きのルールを避ける価値が大きい。

## 結果

- `User` スキーマに `email` が無い。`password_hash` / `deleted_at` も同様
- Entity を直接返さず、必ず `record` DTO に詰め替える運用が必須になる
- 将来メール変更画面を作る場合、`GET /users/me/email` のような**専用エンドポイント**を
  追加し、そこだけ厳格に扱う

## 見直す条件

- メールアドレスの変更・確認機能を実装するとき（専用エンドポイントを新設する形で対応する）
