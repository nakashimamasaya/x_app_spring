# 0005. follow と like を冪等にする

- ステータス: 採用
- 日付: 2026-07-28

## 背景

既にフォロー済みの相手に `POST /users/{username}/follow` が来たとき、
`409 Conflict` を返すか `204 No Content` を返すか。いいねも同じ問題を持つ。

## 決定

follow / unfollow / like / unlike をすべて**冪等**にする。
「既にその状態である」場合も `204` を返し、`409` は使わない。

## 理由

これらの操作は**状態の宣言**であって、リソースの新規作成ではない。
クライアントが求めているのは「フォロー中の状態にする」ことであり、
「フォロー関係というリソースを作る」ことではない。

冪等でない場合、クライアント側に以下の負担が生まれる:

- ボタン連打で `409` が出る → エラー表示するか握りつぶすかの判断が必要
- 楽観的 UI 更新と実際の状態がズレたとき、リトライが `409` で失敗する
- ネットワークリトライで `409` になり、成功したのか失敗したのか区別できない

`409` を返しても、クライアントは結局それを成功として扱うしかない。
**クライアント側で握りつぶされるだけのエラーは、API が返すべきではない。**

## 結果

- 実装は `INSERT ... ON CONFLICT DO NOTHING`。競合状態でも安全に `204` を返せる
- DB の複合主キーによる一意制約違反を、**エラーとして返さず握りつぶす**点に注意。
  例外を握りつぶす実装は普通は悪手なので、コメントで意図を明記すること
- **`DELETE /posts/{postId}` は冪等にしない。** 削除済み投稿への削除は `404` を返す。
  こちらは「状態の宣言」ではなくリソースの削除であり、
  存在しないものを消そうとしたことをクライアントに知らせる価値があるため

一方、**自己フォローは `400`** を返す。これは「既にその状態」ではなく
**論理的にあり得ない要求**なので、握りつぶすとクライアントのバグが隠れてしまう。

## 見直す条件

- フォローに承認フローが入ったとき（申請中という中間状態が生まれ、冪等性の意味が変わる）
