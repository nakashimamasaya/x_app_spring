# 0003. カーソルページングを採用する

- ステータス: 採用
- 日付: 2026-07-28

## 背景

タイムラインと一覧の分割取得方法。オフセット（`?page=2&size=20`）とカーソルのどちらを採るか。

## 決定

すべての一覧でカーソルページングを採用する。カーソルは**不透明な文字列**として定義し、
クライアントによる解釈を禁じる。

## 理由

**オフセットを捨てた理由**: タイムラインは先頭に投稿が追加され続ける。
1 ページ目を見ている間に 3 件投稿されると、2 ページ目の先頭 3 件は 1 ページ目の末尾と重複する。
逆に削除があれば投稿が飛ぶ。「見たはずの投稿がまた出る／見ていない投稿が消える」は
タイムラインとして致命的で、後から直すのは非常に難しい。

深いページで `OFFSET 10000` が遅くなる問題もあるが、こちらは MVP の規模では顕在化しない。
**採用理由は性能ではなく正しさ。**

**カーソルを不透明にした理由**: 中身は UUID の Base64URL エンコードだが、これを公開すると
クライアントがカーソルを自作したり、内部表現に依存したコードを書いたりする。
不透明にしておけば、将来ソートキーを変えたり fan-out on write に切り替えたりしても
クライアントを壊さずに実装を差し替えられる。

## 結果

- 一覧レスポンスは `{ items, nextCursor }` に統一。**次が無い場合 `nextCursor` は `null`**
- `COUNT(*)` を発行しないので総件数は返せない。「全 N 件中」の UI は作れない
- 任意のページへのジャンプができない（無限スクロール前提の UI になる）
- `limit + 1` 件取得して次ページの有無を判定する

総件数が本当に必要になった場合は、専用のカウント API を別途用意する。

## 見直す条件

- 「全 N 件中 M 件目」の表示が要件になったとき
- 任意ページへのジャンプが必要な一覧（管理画面など）が増えたとき
