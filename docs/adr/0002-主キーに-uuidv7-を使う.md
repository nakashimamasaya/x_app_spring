# 0002. 主キーに UUIDv7 を使う

- ステータス: 採用
- 日付: 2026-07-28

## 背景

主キーの選択肢は連番（`bigserial`）、UUIDv4、UUIDv7 の 3 つ。
ID は URL に露出し（`/posts/{id}`）、カーソルページングのカーソルにも使う。

## 決定

すべてのテーブルの主キーに UUIDv7 を使う。

## 理由

**連番を捨てた理由**: ID が URL に出るため、`/posts/1000` が見えると総投稿数が推測できる。
連番を総当たりすれば全投稿を列挙できてしまう。

**UUIDv4 を捨てた理由**: 完全ランダムなので B-Tree インデックスの挿入位置が毎回バラけ、
ページ分割が頻発してインデックスが断片化する。また時系列でソートできないため、
カーソルページングに `created_at` との複合キーが必要になり、クエリが複雑になる。

**UUIDv7 を選んだ理由**: 先頭にミリ秒精度のタイムスタンプを持つため、

- 生成順にほぼ単調増加し、インデックスの断片化が起きない
- **ID だけで時系列ソートできる**ので、カーソルが「最後に返した id」だけで済む
- ランダム部分があるため件数は推測されない

## 結果

カーソルページングが `WHERE id < :cursor ORDER BY id DESC` で書ける
（[0003](./0003-カーソルページングを採用する.md)）。`created_at` との複合キーが不要。

引き換えに、主キーが 16 バイトになり連番（8 バイト）よりインデックスが太る。
MVP の想定データ量（投稿 10 万件）では問題にならない。

**注意**: ID から生成時刻が読み取れる。投稿の作成時刻は元々公開情報なので問題ないが、
時刻を隠したいリソースを将来追加する場合は、そのテーブルだけ別方式を検討すること。

## 見直す条件

- 数千万行規模になり、インデックスサイズがボトルネックになったとき
- 生成時刻を秘匿すべきリソースが増えたとき
